# Coppice 台灣繁體中文技術寫作

> 這份指引放在本倉庫，供 Coppice 專案作者使用。不是全域技能，不登錄外掛市集，也不進入執行階段，也不宣告任何產品功能。來源已全文複核並完成保守替換；原創性、知名度與現行版本的證據仍有下列限度，不宣稱完整鑑定。其他語系用各自的技能：[english-technical-writing](../english-technical-writing/SKILL.md)、[vietnamese-technical-writing](../vietnamese-technical-writing/SKILL.md)、[zh-cn-technical-writing](../zh-cn-technical-writing/SKILL.md)、[zh-hk-technical-writing](../zh-hk-technical-writing/SKILL.md)、[ja-technical-writing](../ja-technical-writing/SKILL.md)、[fr-technical-writing](../fr-technical-writing/SKILL.md)。

## 目標與優先順序

讓讀者知道：這段在回答什麼、該怎麼做、做完會發生什麼，以及哪些條件下不成立。

優先順序：**技術正確與風險完整 → 讀者能理解與操作 → 台灣語境與用語一致 → 精簡。** 不為了口語、簡短或 SEO 改變事實，也不模仿任何一位作者的口頭禪。

這份指引來自 30 篇原先以繁體中文撰寫、面向台灣讀者的技術文章，初次發表均早於 2020-11-07。複核後為 8 位作者、8 個來源網域；以著作、演講與社群／機構刊載支持作者辨識度，不代表稽核過的個人流量。這是當次讀取的現行版本，不保證每個字都與初版相同；可辨認的晚期增補不作舊文措辭依據。參見隨附的 [研究來源與規則依據](references.md)。讀者範圍偏重教學與工程實作；介面短文案的建議另標為延伸，不冒充語料結論。

## 使用流程

### 1. 先看現有內容，不先換字

確認文件目的、讀者程度、平台與版本、現有專案詞彙，以及哪些描述有實作或文件依據。遇到技術矛盾、缺少必要資訊或過期行為，列為待確認問題；不要用順口的句子掩蓋。

動筆前記下不可變動的內容：

- 誰做什麼：使用者、程式、代理程式、瀏覽器、伺服器或作業系統。
- 條件與範圍：平台、版本、必要前置步驟、預設值、例外、時間與執行順序。
- 邏輯與確定程度：不／未／不能／不一定、只有…才、除非、可能、建議、必須。
- 介面與常值：實際按鈕名稱、API、識別字、指令、參數、路徑、網址、數值、單位及錯誤訊息。
- 風險：權限、資料去向、刪除與覆寫、不可復原的影響、驗證與回復條件。

不把「寫作指引」當成增添功能或改變權限的授權。未確認的 Coppice 功能、預設行為、安全保證、效能或支援平台，一律不自行補上。

### 2. 按讀者的問題組織內容〔R01、R07、R08〕

| 內容類型 | 優先交代 | 避免 |
|---|---|---|
| README／快速開始 | 用途、適用情境、最少前置條件、操作與可驗證結果 | 只有口號，或一開始就塞完整架構與所有選項 |
| 入門教學 | 問題為何出現 → 必要概念 → 小範例 → 結果與原因 | 還沒說需求就丟一串專有名詞；反覆假裝困惑 |
| 操作指南 | 目標 → 前置條件 → 步驟 → 預期結果 → 限制 | 只列指令，不說在哪裡執行或如何確認成功 |
| 參考文件 | 定義、輸入／輸出、預設值、範圍與例外 | 硬塞故事、類比或長篇前言 |
| 疑難排解 | 症狀與環境 → 證據／原因 → 處理方式 → 驗證／回復 | 把個案修法寫成一定有效；省略降低安全性的代價 |
| 網站介紹 | 已證實的用途、差異、限制與真實的下一步 | 為了吸引點擊而寫「完全安全」「一鍵解決」等無依據承諾 |

README、網站介紹與參考文件的格式屬 Coppice 編輯延伸，不是這批教學／工程筆記已直接驗證的各體裁規則；網站建議也不是轉換率或 SEO 成效定論。格式可依目的調整；不要求每篇都有「前言、總結、延伸閱讀」。

範例應回答當下的問題。先呈現最小有用結果，再解釋關鍵差異；必要時對照兩種情況。程式碼是片段、忽略錯誤處理或依賴特定版本時，說清楚。類比可以幫助理解，但要回到真實機制，不把比喻當規格。

### 3. 用台灣語境說明，不做機械式轉換〔R02、R03〕

以下是 **Coppice 的建議用語**，不是對所有作者的硬性禁令：

- 一般技術說明優先使用：程式、軟體、程式碼、資料、資訊、檔案、資料夾／目錄、記憶體、變數、陣列、物件、類別、函式、套件、介面、作業系統、儲存庫、權限、預設。
- 依概念選字。資料常指讀取、儲存或處理的內容；資訊可指傳達的內容或背景。兩者不是固定的「原始／處理後」對應。不要把「資訊安全」一律改成「資料安全」。
- 方法、函式與數學上的函數，按技術領域區分；不要為了統一外觀而改掉框架概念。程序、行程、執行緒、程式碼與軟體也不是同義詞。
- 身分驗證與授權、讀取與寫入、回傳與修改、快取與永久保存，各有行為差異。這些區分是正確性要求，不是換一個「比較台灣」的字就完成。
- 同一概念在同一文件保持一致。遇到專案已定義的用語，以現有定義為準；要調整詞彙時，先說明影響。
- 首次出現的陌生概念，可用「中文名稱（English term）」建立對應；之後選一種清楚穩定的稱呼。常見的 API、JSON 等，不必每次重新展開。
- 保留識別字、旗標、檔名、型別、產品名稱與實際 UI 標籤。討論 `error`、`event` 與 `e` 時，拼字就是內容；不能翻掉。
- 不強制消滅英文，也不為了顯得專業，把每個一般動作都換成英文。讀者需要的是能搜尋、能對照、能理解。

### 4. 句子先把行為說清楚〔R04、R05、R06、R09〕

**主詞可省，但換角色要明講。** 同一段連續操作可直接寫「開啟……選取……」。一旦從使用者切到程式、或從程式切到伺服器，要指出誰收到、執行、阻止、儲存或回傳。不要讓「它」同時指向三個物件。非人的代稱以「它」或具體名稱為主，這是專案一致性慣例。

**條件留在對應動作旁。** 長條件可以放前面，再交代結果。保留必要／充分條件的差別：「只有驗證成功後才傳送」不等於「驗證成功就一定傳送」。

**把語氣當作規格的一部分。**

- 「可能延遲」不改成「會延遲」。
- 「預設停用」不改成「建議停用」。
- 「不一定成功」不改成「不會成功」。
- 「這次測試沒有觀察到」不改成「系統不支援」。
- 「官方要求」不改成模糊的「可能需要」。
- 「應該」可能表示推測、預期或建議，要看上下文判斷，不批次替換。
- 計畫、beta、測試中、尚未開放與已正式提供是不同狀態；不把作者的下一步改寫成已出貨的功能。
- 原文明說因果、轉折或先後關係時，要保留該關係；不能只剩兩個並列事實。確認尚未完成，也不等於完全沒有開始確認。

**依推理分句，不訂字數配額。** 當角色、條件分支、時間或論點改變時，考慮分句／分段。緊密的因果或對照可留在一起。刪掉沒有作用的重複起手式；保留真正承接推理的「不過、因此、也就是說」。不禁用「透過、進行、基本上、其實」，逐句判斷它是否提供條件或只是繞路。

### 5. 自然不等於裝熟〔R10、R11〕

- 用直接的動詞：開啟、選取、確認、設定、儲存、執行。「可以」可能指能力、許可或選項，要依上下文保留原意；能做不等於獲准做。需要禮貌時用「請」，不靠禮貌詞模糊義務。
- 問句適合引出下一個要回答的問題，不是每個標題的固定樣板。
- 第一人稱只用於真實的測試、觀察或設計取捨。不虛構「我也踩過這個坑」。
- 不加入錯字、假猶豫、固定數量的表情符號、喔／啦／呢，或抄作者的玩笑來製造人味。
- 不用「聰明的讀者」「這很簡單」評價讀者，也不以戲謔語氣取代風險說明。工程筆記能輕鬆，權限與刪除警告仍要直接。

**Coppice 排版慣例：** 中文正文使用全形中文標點；短 UI 標籤可用「」；識別字與常值用反引號；中文與 Latin token 之間在適當處留一般空格。來源作者的排版並不完全一致，這不是語料的絕對規則。不要讓排版取代程式碼裡的 `::`、`>=`、`--`、引號、路徑或 Markdown 語法。

### 6. 風險不能被精簡掉〔R12〕

這一節是 Coppice 的安全編輯政策，由來源中的正反例支持其需要，不是所有作者共同遵循的文風定律。保留警告強度、對象、影響範圍、權限與回復條件。需要降低安全性或會刪除資料的操作，警告應在操作之前，不藏在括號或文末。

來源缺少必要警告時，標出來請技術審查；不要自行發明備份流程、安全邊界、成功保證或一個其實不存在的「允許」按鈕。

**介面短文案延伸：** 在已知且有依據時，交代目前狀態、哪個動作未完成、原因與真實下一步。不要把「尚未更新」改成成功訊息，也不要預設重新登入／重試一定能排除問題。這是從工程說明推導的編輯原則，尚無代表性 UI 語料驗證。

### 7. 改完對照語意，再交付

逐項檢查：

- 角色、動作、輸入／輸出、資料去向有沒有改變？
- 平台、版本、預設值、範圍、比較符號、數值、單位與執行順序是否保留？
- 否定、例外、必要條件、可能性與建議強度是否一致？
- 警告、驗證狀態、權限及不可復原的後果是否仍完整？
- 程式碼、識別字、連結、UI 標籤與 Markdown 結構是否未被排版破壞？
- 是否新增了沒有依據的產品功能、經驗、支援範圍或 SEO 承諾？
- 讀者能否辨認這段回答的問題與下一步？精簡是否真的降低理解負擔？

交付時分開說明「措辭／結構調整」與「仍待確認的技術問題」。有測試或驗證就列出實際做過的；沒有就明說，不把文字審查說成執行驗證。

## 自製練習：只測措辭，不描述 Coppice 功能

下列全是虛構的一般工具例句；不是產品規格，也不是取自來源作者的段落。

| 原句 | 可接受的修改 | 不可改成 |
|---|---|---|
| 當設定檔不存在的情況發生時，工具不會進行資料夾建立，也不會進行連線。 | 設定檔不存在時，工具不會建立資料夾，也不會連線。 | 找不到設定檔時會重新連線。（改了條件與否定） |
| 在 Linux 平台上，此選項在預設的情況之下為停用。 | 在 Linux 上，此選項預設停用。 | 此選項在所有平台都停用。（擴大範圍） |
| 重新啟動可能可以排除此問題，但目前尚未完成確認。 | 重新啟動可能排除此問題，但目前尚未確認完成。 | 重新啟動即可修復。（移除不確定性） |
| 本函式會回傳新的陣列，不會對原陣列進行修改。 | 本函式會回傳新陣列，不會修改原陣列。 | 本函式會更新陣列。（混淆回傳與修改） |
| 此範例允許的版本大於或等於 1.4，且小於 2.0。 | 此範例允許 `>= 1.4` 且 `< 2.0` 的版本。 | 支援 1.4 到 2.0。（界線不明，且把範例提升成支援承諾） |
| 目前帳號沒有寫入權限，因此檔案尚未更新。 | 目前帳號沒有寫入權限，因此檔案尚未更新。 | 請重新登入即可。（介面延伸；自行編造修法） |

## 規則依據與適用限度

R01–R12 的原文定位、不同寫法與反例，見隨附的 `references.md`。來源支持的是說明的功能，不是每個字都值得照做：歷史文章也有拼字、範例、預測與風險提示上的缺陷。這份技能不設定句長配額、不模仿單一作者、不複製完整文章，也不把台灣繁體寫作當成簡體字轉換工作。
