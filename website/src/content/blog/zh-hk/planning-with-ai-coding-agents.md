## 為甚麼要先做計劃

代理一開始就寫程式，理解錯了只會在 diff 裏出現。到那個時候，它已經把不對的東西做出來。你要花時間讀、解釋原本的意思，再等下一次嘗試。計劃把同一個誤解收成幾行，一分鐘就讀完。

拿到計劃並不難：你開口要，任何代理都會寫。難的是讓它有用。要求含糊，代理就不問而猜；計劃只排步驟，不寫背後的決定；一開始寫程式，也沒有人再拿程式碼對着計劃檢查。

## 好計劃裏有甚麼

- **用你自己的話說出結果和限制。**「Settings 裏加一個深色模式開關，跟應用其餘部分用同一套主題設定。」
- **要答案，不要猜測。** 代理做計劃之前，先問它需要知道的事。
- **寫出方針，以及為甚麼這樣選。** 真有選擇時，例如版面或資料模型，代理列出選項並推薦一個。
- **幾個步驟，包括能顯示改動有效的測試。**
- **它不會改甚麼。**

一兩分鐘讀不完，這項工作就可能太大。把它拆開。

## 做法一：CLI 的計劃模式

Claude Code 有計劃模式：代理讀程式碼、提出計劃，但不改檔案。其他代理則要你先要一份計劃，並說明在你批准之前不要改任何東西。

這是最快可以開始的做法。限制是計劃只留在對話裏。工作階段結束，計劃就消失，最終的 diff 也不容易再對着它檢查。

## 做法二：在倉庫裏放一份計劃檔案

叫代理把計劃寫進 Markdown 檔案，例如 `docs/plans/dark-mode.md`。你自己改這個檔案，再用「Implement docs/plans/dark-mode.md」開始寫程式。同一個代理可以做，換一個也可以。

計劃會留住，跨過工作階段，也跨過不同的代理。你可以像審程式碼一樣審它。檔案仍由你管，甚麼時候算批准由你決定，diff 和計劃的對照也要你自己做。

## 做法三：用 Coppice，把計劃做成你批准的一步

[Coppice](/) 是一套桌面軟件，把程式設計代理放在同一塊工作看板上。每張工單都由一份計劃開始。PM 代理可以先問你最多三個問題，然後才寫計劃。介面改動還會給出幾種設計方案，供你比較和挑選。這次規劃不會改你的程式碼。你批准之後，計劃就存在工單上。代理按它來構建，你再對着計劃審查 diff。

1. [安裝 Coppice](/docs/install)，並加入你的專案。
2. 寫一張工單，寫明結果和限制，然後讓代理開始工作。
3. PM 代理如果發問，就回答。
4. 讀計劃。介面改動可以打開設計方案並選一個。然後批准計劃，或要求修改。
5. 程式碼準備好了，就對着已批准的計劃審查 diff。

## 選哪一種

- **一個工作階段裏的小工作：** 計劃模式。
- **跨工作階段或跨代理的較大工作：** 一份計劃檔案。
- **工作多，而且寫任何程式之前，計劃都是你要批准的一步：** 用 Coppice。由[快速上手](/docs/getting-started)開始。
