## 为什么难

智能体写代码比你读得快。一个小要求可能回来变成一大份 diff，里面有你没要求的改动，摘要却说一切正常。逐行读太慢。扫一眼又会漏掉错误。

难的是知道智能体本来该做什么。没有这一点，你分不清某项改动该不该出现在 diff 里，还是没人要求的范围。

## diff 里要检查什么

无论用哪种方式审核，都看这些：

- **范围。** 你没料到的文件，比如 lockfile、迁移、配置，或重命名。
- **错误路径。** 输入缺失、调用失败，或值为空时会怎样。
- **依赖和访问。** 新的包、脚本、凭据，或谁能读取、谁能修改数据的变化。
- **测试。** 真正跑过这次改动的测试，而不只是摘要里说测试通过的那一行。

## 做法一：在 git 或 pull request 里审核

把智能体的分支和你的主分支做 diff，或者开一个 pull request，像审同事的工作那样审。任何智能体、你已经在用的任何工具都可以。

限制是你只看得到结果。你要求的内容留在聊天记录里，所以你是拿 diff 去对记忆里的那次要求。

## 做法二：先让第二个智能体审核

在你自己看之前，让另一个智能体先审这份 diff，比如用 Codex 审 Claude Code 写的内容。它能抓住明显的问题，并给你一份该看的位置清单。

它的审核是第二意见，不是签字放行。diff 还是要你读，决定也还是你做。

## 做法三：用 Coppice，先批准计划

[Coppice](/) 是一个桌面应用，把编程智能体放在一块任务看板上。写任何代码之前，智能体先写计划，由你批准。工作做完后，Coppice 把 diff 放在你批准的计划旁边，并标出计划里没提到的文件。接受这次工作并不合并，什么时候进主分支由你决定。

1. [安装 Coppice](/docs/install)，并加入你的项目。
2. 写一张工单，让智能体开始做。PM 智能体写出计划。
3. 读计划。批准它，或要求修改。
4. 工单进入 Wait for Human Review（等待人工审核）之后，审查代码。在行上写评论，或接受这次工作。
5. 准备好了再合并。

看起来是这样。工单要在 Settings 里加一个深色模式开关。PM 智能体的计划有三步：加上开关、沿用现有的 theme hook、再加上一项设置测试。

## 该选哪一种

- **一个智能体的小改动：** 在 git 或 pull request 里审核。
- **改动较大，而且你想先有人过一遍：** 让第二个智能体看，然后你自己再读。
- **智能体的任务很多，而且你想在写代码之前先就计划达成一致：** 用 Coppice。从[快速上手](/docs/getting-started)开始。
